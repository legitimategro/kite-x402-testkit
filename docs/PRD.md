# 05 · x402 联调与故障测试套件

PRD 1.0 · 2026-10-18 · 开发测试基础设施 · 第一批或第二批  
状态：设计提案，未实现/未付款/未提交。先读[总体接入设计](../总体接入设计.md)与[接口事件约定](../接口与事件约定.md)。

## 1. 用户与真实场景

**用户：**开发 x402 服务或语言组件、希望在上线前验证成功与失败行为的维护者。

**第一次使用：**开发者配置一个待测服务，套件让上游延迟、返回 500、断开响应，再检查服务是否提前收费、是否错误重试、是否暴露密钥。

**问题：**只验证一次 402 和一次付费成功，发现不了失败时的结算顺序、金额转换和响应丢失。模拟测试与真实付款也经常被混用。

**Kite 接入价值：**独立资产是故障场景、断言、原始协议证据和跨实现契约；它不替代 facilitator，也不重复实现 Passport Skills 的自然语言行为 Runner。

## 2. MVP 范围

**P0，首版必须完成：**

- 离线协议桩与故障上游：超时、坏 JSON、4xx/5xx、慢响应、连接重置。
- 待测服务适配器记录调用顺序，对 verify/业务/settle 关系作确定性断言。
- 真实集成模式使用获批环境及预算，只运行显式批准的付款测试。
- JSON/JUnit/HTML 报告区分 mock_pass、live_pass、blocked、failed，CI 不把 blocked 当真互通。

**P1，有真实反馈后再做：**

- 在出现真实兼容问题后扩充语言组件矩阵和版本基线。
- 新增 SIWX/异步专项需要独立协议向量与真实互通，不默认启用。

**首版排除：**不建立新 facilitator，不把测试绿灯当官方准入，不重复做已有全量 Skills Runner。

## 3. 完整用户流程

1. 固定待测版本和网络配置，选择离线或真实模式。
2. 离线模式启动可控上游和协议桩，加载带预期的场景。
3. 运行请求，收集待测服务日志与协议观察点。
4. 断言付款、业务结果、错误和敏感信息处理。
5. 获批后对真实 facilitator 与 Passport 路径做独立集成验证。
6. 导出带来源及环境的报告；失效用例保留可复现输入。

## 4. Kite 能力接入

| 官方能力 | 接入方式 | 保存与验证 |
|---|---|---|
| 卖方兼容 | 官方模板行为与实际 facilitator | 真实 supported/verify/settle 与离线桩严格分开 |
| 买方验证 | 固定版本 kpass session execute | 真实会话、付款与商家返回，不从桩生成假交易哈希 |
| CI | 项目自建 runner 与 JUnit | 不称为官方认证，不替代官方全量 Skills eval |

**接入前置：**所有涉及真实付款的路径先完成 G0，固定 network/asset/facilitator/CLI/账户环境；见总体接入设计。真实身份或 Runtime 不可得时明确 blocked，不能用 mock 替代。

**授权边界：**应用与业务权限自己验证；Passport 的 passkey 批准保留给真实用户；本轮 PRD 编制不发起任何授权或支付。协议实例、金额、会话和示例均以现场预检与实际输出为准。

## 5. 接口与数据

**拟提供接口：**拟提供 testkit run --profile offline|live --target <url> --suite <file>；这是自建 CLI。live 必须有指定环境与预算输入；接口不接受“无上限跑全部付款用例”的隐式默认。

**核心对象：**SuiteVersion、Case、FaultPlan、ObservedEvent、Assertion、RunProfile、BudgetEvidence、Report。每例包含预期、证据来源、是否实际支出。

operation_id、付款证据、业务版本及产物按公共事件契约关联。接口/包名属于本项目设计，不代表官方已经发布同名能力。

## 6. 状态与恢复

PLANNED → ENV_CHECKED → RUNNING → ASSERTED → REPORTED；每例 PASS/FAIL/BLOCKED/SKIP；报告另标证据等级，不能把离线 PASS 汇总成 LIVE PASS。

- 不对未经授权第三方做故障注入；只操作自有服务或明确获准的测试目标。
- 真实结算无法由本地桩推断；观察不到时 blocked，不写“未收费”。
- 付款结果不明立即停止该操作后续重试；保留原 key、响应和请求摘要。

任何付款未知均不能通过换 key 自动重买；任何产物恢复都需要原权限。测试桩中的假付款不产生真实交付承诺。

## 7. 开发任务拆分

- 05-T01：建立受支持契约与故障表，设计错误实现对照。
- 05-T02：实现故障上游和最小协议桩，避免复制现成业务服务。
- 05-T03：实现事件观察和断言。
- 05-T04：实现 CI、JUnit 与脱敏证据存储。
- 05-T05：真实小额联调并验证一项语言组件。

**投入粗估：**4–6 人周。先做 M0 兼容与样本验证，再做独立核心、真实互通及发布；外部批准、环境开通和审核不计入可承诺工期。

## 8. 界面与使用体验

命令行为主，HTML 展示每例的调用顺序、预期与实际、支出和证据。

在需要用户决定时展示价格、范围、权限和失败状态；普通产品页面不堆协议实现细节，技术证据留在诊断/报告页。

## 9. 验收与演示

下面是目标，尚未运行或达成。

- T01：至少覆盖正常 402、无效签名/网络/金额、上游失败、响应丢失、结算未知和重复请求。
- T02：故意破坏结算顺序的样例实现必须被断言抓到。
- T03：离线与真实证据在文件和 UI 中不混淆，报告不能凭空补交易参考。
- T04：真实环境可达时完成一个最小付款集成；不可达则 CI/报告明确 blocked。

**完整演示：**同一套件分别测试正确服务和提前结算的故障服务，展示确定性的差异及独立真实集成证据。

**试用观察：**能发现的真实兼容回归、故障复现稳定性、维护者定位用时和用例误报。

## 10. 提交与独立性

开发工具/模板测试贡献；可以作为原组件测试资产扩展，不为拆分数量新建同一测试器。

项目核心包括本 PRD 定义的模型、业务引擎/状态/断言与样本；支付和基础依赖可正常共享，不复制其他参赛实现换名。EC 映射、活动审核与真实贡献是否被统计分别跟踪，不用本 PRD 保证收录。
